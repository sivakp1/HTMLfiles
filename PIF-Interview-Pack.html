LLM Prompt-Injection Firewall (PIF)

A service that inspects untrusted text before it reaches an LLM and decides to allow, flag, sanitize or block it, with a reason for every verdict. Built with spec-driven development in one week: detection backend on AWS, dashboard on Vercel, evaluation built in from day one.

Method Spec-driven development Backend AWS Lambda, Bedrock, DynamoDB, CDK Dashboard Next.js 15 on Vercel Size ~9,000 lines across 5 parts

The whole design follows from one fact: an LLM reads instructions and data as a single stream of text, so anything it reads can try to give it orders. A user can type "ignore your previous instructions", and a fetched web page can hide the same sentence in white text. No parameterized-query equivalent exists, so the firewall reduces risk in layers and the rest of the system limits damage when something gets through.

One request, end to end

  1. AuthorizerHashes the API key, finds the app. Bad key is passed on as invalid so the API can return a proper 401.
  2. OrchestratorValidates the body, re-checks the key, loads the app policy (cached 60 s).
  3. Core scannerNormalizes text, runs 35 rules, batches chunks to the classifier, asks the judge only in the gray zone.
  4. DecisionFuses scores, applies the trust-aware table, spotlights or drops risky documents.
  5. Verdict logStores a keyed hash and a redacted snippet, never the prompt. A stream updates hourly stats.

Architecture decision records

Design decisions, with the alternatives

Each record states what was chosen, what was rejected, what it costs, and the spec IDs that make it testable. Open the ones you expect to be asked about.

ADR-01Build a prompt-injection firewall rather than another cloud scannerScope
Options
IaC misconfiguration scanner, PR secrets guard, CloudTrail mini-SIEM, SBOM risk triage, prompt-injection firewall.
Decision
The firewall.
Why
It has public labeled datasets (deepset, Gandalf, JailbreakBench, BIPIA), so detection quality is measurable within a week. AWS offers a ready baseline in Bedrock Guardrails. It is also the OWASP Top 10 for LLM Applications' first risk, so the problem is current.
Cost
Detection is probabilistic. Results must report false positives as prominently as catches.

ADR-02Spec-driven development with numbered requirements and enforced traceabilityProcess
Options
Code first with a README; lightweight user stories only; full SDD (constitution → spec → plan → tasks).
Decision
Full SDD: principles P1–P9, requirements CORE / BE / FE / EVAL / NFR, Given/When/Then acceptance criteria, and a CI script that fails if any criterion has no test.
Why
A one-week build moves fast and AI-assisted coding drifts without a contract. Test names carry their criterion ID, so "is it done?" is answered by CI, not by opinion.

Days 1–2 produce documents, not code. Every scope change costs a spec revision first.

ADR-03Dashboard on Vercel, detection and data on AWSArchitecture
Options
Everything on AWS (Amplify or S3 + CloudFront); everything on Vercel with an external LLM API; split.
Decision
Split: Next.js dashboard on Vercel, Lambdas, Bedrock, DynamoDB and Cognito on AWS, all infrastructure in CDK.

Two platforms to configure. Cognito callback URLs cannot use wildcards, so random preview URLs cannot sign in.

ADR-04Three detection layers, with the LLM judge used only in a gray zoneDetection
Options
Regex only (fast, easily evaded); one classifier (no explanations); LLM judge on every input (slow, costly).
Decision
L1: 35 rules in 9 categories (milliseconds). L2: ONNX classifier on CPU (tens of ms). L3: a Bedrock Claude judge only when the pre-score is 0.30–0.80, at most 3 segments per request.
Why
Clear cases are settled cheaply; the judge spends its latency where it changes the outcome and supplies the human-readable reason analysts need.
Cost
More moving parts. Each layer can fail independently, so failure handling had to be designed (ADR-12).
Trace
CORE-09…19AC-CORE-4AC-CORE-5NFR-04
ADR-05A simple, pure fusion formula instead of a learned combinerDetection
Options
Weighted average; a trained meta-model; max of layer scores plus judge adjustment.
Decision
Rules combine by noisy-OR, pre-score p = max(h, c), an injection verdict lifts risk to at least 0.5 + 0.5·conf, a benign verdict caps it at 0.5 − 0.5·conf, critical rules floor it at 0.95.
Why
Explainable on a whiteboard and unit-testable from a table. The benign path is what rescues false positives such as "I'm a student, what is prompt injection?" (pre-score 0.35 → 0.05).
Cost
Hand-set constants. The threshold sweep in evaluation is what justifies them.
Trace
CORE-11CORE-20CORE-21spec A.11
ADR-06Actions depend on where the text came fromDetection
Options
One action ladder for all input; block the whole request on any hit.
Decision
User text can only be flag or block. Retrieved documents are sanitized (cleaned, or dropped above 0.85). LLM output is blocked from 0.70.
Why
You cannot meaningfully sanitize what a user typed. A poisoned web page, though, usually still holds useful content, so dropping only the bad part keeps the product working.
Cost
A sanitized document can lose context. Apps that prefer safety can set block_on_context.
Trace
CORE-23CORE-24US-02
ADR-07Normalize and unpack text before any rule runsDetection
Options
Match on raw text; rely on the classifier to cope with obfuscation.
Decision
NFKC, strip zero-width and bidi characters, decode Unicode tag characters (ASCII smuggling), extract hidden HTML, decode base64 / hex / percent runs to depth 2, and match rules on a homoglyph- and leetspeak-folded copy.
Why
Obfuscation is the cheapest attacker move. Hidden and decoded text becomes its own "derived segment", so findings point at exactly where the attack was. Folding keeps length 1:1, so match positions map back to the original text for highlighting.
Cost
More segments per request, so more classifier chunks.
Trace
CORE-04…08AC-CORE-2AC-CORE-3
ADR-08Defence beyond detection: spotlighting, canary token, link checksSecurity
Options
Detection only; detection plus output filtering.
Decision
Wrap untrusted content in delimiters carrying a per-request random nonce (and strip look-alike delimiters). In proxy mode, plant a canary in the system prompt and block any reply containing it; neutralize links to unknown domains and block data-bearing ones.
Why
Detection will miss some attacks. These layers limit what a missed attack can achieve: prompt leaks and data exfiltration through rendered images are caught on the way out.
Cost
Spotlighting depends on the downstream model honouring the instruction; it lowers risk rather than removing it.
Trace

ADR-09Detection logic as a pure library with injected layersArchitecture
Options
Logic inside the Lambda handler; a shared service.
Decision
pif_core has no AWS imports. The classifier and judge are passed in through small interfaces; the Lambda supplies AWS-backed versions, tests supply mocks.
Why
The spec's worked examples run as unit tests with mocked layer scores, and the local evaluation CLI scores exactly like the cloud runner.
Cost
A thin adapter layer (pif_lambda) to maintain.

ADR-10Never store raw promptsPrivacy
Options
Store full prompts for analysis; store nothing.
Decision
Store an HMAC-SHA256 of the input (pepper in Secrets Manager) and a 200-character snippet with emails, phone numbers (including +91), Luhn-valid cards, Aadhaar-like numbers, AWS keys and JWTs redacted. Verdicts expire after 30 days. Logs never contain text.
Why
Prompts often contain personal data. A security tool that becomes a data store of everything users typed would be a new risk.
Cost
Analysts cannot see the full input; they reproduce cases in the playground.

P1BE-07BE-08AC-BE-3AC-BE-12
ADR-11Two API planes; the dashboard holds no API keysSecurity
Options
One API with API keys everywhere; dashboard calling AWS from the browser.
Decision
Data plane (/v1/scan, /v1/chat) uses per-app keys stored only as hashes, with a 24-hour rotation grace. Control plane (/v1/admin/*) uses the signed-in user's Cognito token with admin and analyst roles. The browser only calls the dashboard's own server routes, which validate every response.
Why
A leaked dashboard cannot be used to scan or to impersonate an app, and CI fails the build if a key pattern appears in the client bundle.
Cost
HTTP API authorizers can only deny with 403, so invalid keys are passed through and the orchestrator returns the 401 the spec requires.

ADR-12Explicit failure behaviour and a monitor modeArchitecture
Options
Always fail open; always fail closed.
Decision
Each app chooses fail_mode open or closed. Any missing layer sets degraded: true in the response. Monitor mode computes the verdict but always allows, returning would_action.
Why
A support bot and a payments assistant need different trade-offs. Monitor mode lets a team measure false positives on real traffic before enforcing.
Cost
Callers must read the degraded flag to know a verdict had fewer layers.

ADR-13Analytics updated asynchronously from a DynamoDB streamArchitecture
Options
Update counters inside the scan; query raw verdicts for charts.
Decision
The scan path does one write. A stream-triggered Lambda adds hourly counters and a fixed-bucket latency histogram to a stats table.
Why
Keeps scan latency inside budget, and a failed verdict write never fails a scan. Charts read small pre-aggregated rows.
Cost
Analytics lag by seconds; p95 is approximated from histogram buckets.

ADR-14Attack text is only ever rendered as plain textSecurity
Options
Render markdown for readability; sanitize HTML before rendering.
Decision
React text nodes only, highlights built by cutting strings at offsets, react/no-danger as a lint error, and a per-request nonce Content Security Policy.
Why
A firewall dashboard displays attacks all day. Rendering one would turn the security tool into the victim.

ADR-15Evaluation designed before tuning, with a regression gate in CIEvaluation
Options
Spot-check examples; one accuracy number at the end.
Decision
Versioned datasets with attacks, plain benign prompts, hard negatives and a 100-item self-written holdout. Four configurations (L1, L1+L2, L1+L2+L3, Bedrock Guardrails), a threshold sweep from stored scores, and a CI gate that fails if recall drops more than 2 points or false positives rise more than 1 point.
Why
The ablation shows what each layer earns, the baseline answers "why not just use Guardrails?", hard negatives expose false positives, and the holdout checks the thresholds were not fitted to public data.
Cost
Dataset building takes time; BIPIA needs a local export.

Own these before you are asked

Known limits and what you would do next

Found in the code review or stated in the README. Raising them yourself shows the review was real.

New API key rejected for up to 60 s

Warm orchestrators cache the app record, so a just-rotated key fails until the cache expires. Fix: on a key mismatch, re-read the app before rejecting.

Throttling is per API, not per key

HTTP APIs cannot throttle by key, so one noisy app shares the 50 rps limit. Fix: a REST API usage plan or a DynamoDB token bucket.

Old default judge model

The config ships with Claude 3 Haiku. Fix: set a current Haiku-class model or APAC inference profile in cdk.json, then re-run evaluation.

Approximate chunking

The core has no tokenizer and estimates tokens conservatively; the classifier also truncates at 512. Fix: share the classifier's tokenizer if chunk boundaries start to matter.

Single turn, no output judge

Only the last user message is scanned and the judge never sees LLM output. Next: sliding-window scans over conversation history.

Evaluation numbers not yet produced

Detection targets are in the spec, but the full dataset and the first cloud run are still to do. Before the interview: run it and quote real figures.

Interview kit

Two-minute pitch

LLM apps treat everything they read as possible instructions, so a user, or a web page the app fetches, can take over the model. I built a prompt-injection firewall that sits in front of any LLM app and decides, for each piece of text, whether to allow, flag, sanitize or block it, with a reason.

Detection runs in three layers: fast rules, a small classifier, and an LLM judge that is only consulted when the first two are unsure. That keeps typical latency low and cost predictable. Because a user's message and a retrieved document carry different risks, the action depends on where the text came from: documents are cleaned rather than rejected, and outputs are checked for prompt leaks with a canary token.

I built it with spec-driven development: nine principles, numbered requirements and acceptance criteria, and CI that fails if any criterion has no test. It runs on AWS Lambda and Bedrock with a Next.js dashboard on Vercel, never stores raw prompts, and is evaluated against public datasets, hard negatives and AWS's own Bedrock Guardrails as a baseline.

Interview kit

Likely questions

Short answers you can expand from. Each one points back to a decision record.

Why not just use Bedrock Guardrails?

It is the baseline in the evaluation, on the same data. The firewall adds what Guardrails does not give out of the box:

  • a reason per verdict, from rules or the judge;
  • per-app thresholds and monitor mode;
  • sanitizing a poisoned document instead of rejecting the whole request;
  • canary and exfiltration-link checks on output.

If Guardrails scores better on recall, say so and explain where the layers still add value. (ADR-01, ADR-15)

Walk me through one request.

Key hash → app and policy → normalize and unpack text → 35 rules → classifier on batched chunks → judge only for gray-zone segments → fuse into one risk → trust-aware action → sanitize documents → store hash and redacted snippet → stream updates stats. Use the five-box path at the top of this page. (ADR-04, ADR-06)

How do you keep false positives down?
  • Hard negatives in the dataset, measured separately.
  • A confident "benign" from the judge pulls risk down (0.35 → 0.05 in the student example).
  • Mid scores flag rather than block.
  • Per-app allow phrases that suppress named rules only.
  • Monitor mode before enforcing; thresholds chosen from the sweep.

(ADR-05, ADR-12, ADR-15)

Can an attacker inject the judge itself?

The judge reads the text inside delimiters with a random nonce and is told never to follow instructions there. Its reply must match a strict JSON schema or it is treated as "uncertain". It can only move a score; it cannot trigger actions. Critical rules skip the judge entirely, and the canary still guards the output. (ADR-04, ADR-08)

What happens when the classifier or Bedrock is down?

The result is marked degraded. With fail-open the scan continues on the layers that work; with fail-closed and no usable layer, the API returns 503. Timeouts are 800 ms for the classifier in prod and 2.5 s for the judge, with no retries on the hot path. (ADR-12)

How do you know it works?

Two kinds of evidence. Behaviour: every acceptance criterion has a test, and CI fails if one is missing. Quality: the ablation across L1, L1+L2 and L1+L2+L3 against Guardrails, with recall per attack category and false positives on hard negatives, plus the self-written holdout for generalization. (ADR-02, ADR-15)

How do you protect user data?

No raw prompts are stored. Inputs are kept as a keyed hash plus a short redacted snippet, verdicts expire after 30 days, logs carry no text, everything is encrypted with a customer-managed KMS key, and the dashboard never renders attack text as HTML. (ADR-10, ADR-14)

Why spec-driven development, and did it pay off?

A one-week build with AI help needs a fixed contract. Writing the decision table forced an early choice about what "sanitize" means for a user's own message, and the code review compared the implementation against numbered requirements rather than impressions. The cost was two days of documents before code. (ADR-02)

What would you change with more time?

Fix the key-rotation cache, add per-key throttling, scan conversation history, run the judge on output for high-risk apps, and support streaming responses. Pick two from the Known limits section and explain the fix.

What does it cost to run?

Dev is pay-per-request. Prod keeps one 3 GB classifier instance warm, a few tens of dollars a month. Per-request cost is measured by the evaluation runner from Lambda time and judge tokens; the spec's target is under US$1 per 1,000 scans at 20% judge escalation. Quote the measured figure once you have it.
