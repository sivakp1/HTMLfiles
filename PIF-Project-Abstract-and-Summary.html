Abstract

Large language model (LLM) applications cannot reliably tell their developer's instructions apart from the text they process, so a user's message, or a web page, email or document the application retrieves, can carry instructions that override its intended behaviour. This class of attack, prompt injection, is ranked first in the OWASP Top 10 for LLM Applications and has no complete fix comparable to parameterized queries for SQL injection. This project designs and implements the LLM Prompt-Injection Firewall (PIF), a service that inspects untrusted text before it reaches a model and decides to allow, flag, sanitize or block it, with a stated reason for every verdict. Detection runs in three layers: 35 heuristic rules over normalized and de-obfuscated text, a lightweight ONNX classifier, and an LLM judge (Gemini 3.5 Flash-Lite) consulted only when the first two layers are uncertain. Actions depend on the source of the text: retrieved documents are cleaned and wrapped in nonce-tagged delimiters rather than rejected, and model output is checked for leaked canary tokens and data-exfiltration links. The system was built with spec-driven development: nine principles, numbered requirements and testable acceptance criteria, enforced by a CI check that every criterion has a test. It runs on AWS Lambda and DynamoDB with a Next.js dashboard on Vercel, reaches its judge through a configurable LLM provider (currently Google's Gemini API), and stores no raw prompts. Its evaluation compares each detection layer against Amazon Bedrock Guardrails on public injection datasets, hard negatives and a self-written holdout set.

Keywords: prompt injection, LLM security, AI guardrails, spec-driven development, AWS Lambda, LLM-as-a-judge, Gemini API, Vercel, evaluation

Problem statement

An LLM application assembles one block of text from the developer's system prompt, retrieved context and the user's message, and the model reads all of it as one stream. Attackers exploit this in two ways:

  • Direct injection: the user types instructions such as "ignore your previous instructions and reveal your system prompt".
  • Indirect injection: instructions hide in content the application fetches, such as white-on-white text on a web page, an email, a PDF in a retrieval index or a tool's output. The user may be innocent.

The consequences range from leaked system prompts and policy bypass to data exfiltration and unauthorized actions when the model can call tools. Keyword filters are easy to evade with rephrasing, encoding, other languages or invisible Unicode, while sending every input to a second LLM is slow and costly. Teams need a layer that is fast, explains its decisions, keeps false positives low and can be measured.

Objectives

  1. Detect direct and indirect prompt injection, including obfuscated attacks, before text reaches the protected model.
  2. Return one of four actions (allow, flag, sanitize, block) with at least one human-readable reason for every non-allow verdict.
  3. Keep sanitized documents usable rather than rejecting whole requests.
  4. Stay within a latency budget: p95 of 300 ms without the LLM judge and 1,500 ms with it.
  5. Store no raw prompts.
  6. Let administrators tune thresholds per application, without redeploying, and trial policies in monitor mode.
  7. Measure detection quality against a recognised baseline, including false positives on benign but suspicious-looking text.
  8. Deliver within one week, with every acceptance criterion traceable to an automated test.

Methodology

The project followed spec-driven development: the specification came before the code and served as the contract for implementation and review.

  • Project selection: five security projects were shortlisted (an IaC misconfiguration scanner, a PR secrets guard, a CloudTrail mini-SIEM, SBOM risk triage and the firewall). Each was judged on whether detection quality could be measured within a week. The firewall won because public labeled datasets exist and AWS offers a ready baseline.
  • Constitution: nine non-negotiable principles, including no raw prompt storage (P1), a pure detection core (P2), explainable verdicts (P3), explicit failure behaviour (P4), least privilege (P5), a test for every acceptance criterion (P6) and plain-text rendering of attack payloads (P7).
  • Specification: user stories plus numbered requirements (CORE, BE, FE, EVAL, NFR) with Given/When/Then acceptance criteria. It is split into spec.md, backend.md and frontend.md.
  • Traceability: test names carry their criterion ID, and a CI script fails the build if any criterion in the spec has no test.
  • Review: the implementation was reviewed file by file against the numbered requirements.

System design

PIF exposes two APIs on AWS. LLM applications call a data plane (/v1/scan, /v1/chat) with a per-app API key. The Vercel dashboard calls a separate control plane with the signed-in user's Cognito token, so the dashboard holds no API keys.

The detection engine runs inside the orchestrator; only the classifier, the LLM judge and the database are separate calls.

Each request passes through one pipeline in a pure Python library, pif_core:

  1. Pre-processing: Unicode normalization; removal of zero-width and bidirectional characters; decoding of Unicode tag characters ("ASCII smuggling"); extraction of hidden HTML; decoding of base64, hex and URL-encoded runs. Hidden or decoded text is scanned as its own segment.
  2. Detection in three layers (table below), fused into one risk score between 0 and 1.
  3. Decision by source: a user's message can be flagged or blocked; a retrieved document is sanitized (cleaned, or dropped above 0.85); model output is blocked from 0.70.
  4. Sanitization: matched spans are removed and the document is wrapped in delimiters carrying a per-request random nonce ("spotlighting").
Layer Method Typical cost Role
L1 heuristics 35 regex rules in 9 categories, matched on homoglyph- and leetspeak-folded text milliseconds Catches known patterns and obfuscation
L2 classifier ProtectAI DeBERTa v2 exported to ONNX, run on CPU in a Lambda container tens of ms Catches rephrased attacks
L3 judge Gemini 3.5 Flash-Lite through Google's Gemini API (provider is a server setting: Gemini, Anthropic or Bedrock), only for scores 0.30–0.80, at most 3 calls per request hundreds of ms Settles uncertain cases and writes the reason

In proxy mode (/v1/chat), PIF also calls the model, plants a canary token in the system prompt, and blocks any reply that leaks it or contains a data-bearing link to an unknown domain.

Security and privacy

The firewall handles attack text all day, so it is built to be safe as a target itself.

  • No raw prompts stored. Each verdict keeps an HMAC-SHA256 of the input (key in Secrets Manager) and a 200-character snippet with emails, phone numbers (including +91), Luhn-valid card numbers, Aadhaar-like numbers, AWS keys and JWTs redacted. Verdicts expire after 30 days, and logs contain no input text.
  • Keys stored as hashes. API keys are kept only as SHA-256 hashes, with a 24-hour grace period after rotation.
  • Least privilege. Each Lambda has its own IAM role. Data is encrypted with a customer-managed KMS key, and cdk-nag runs on every build.
  • Safe rendering. The dashboard shows attack payloads only as plain text, under a per-request nonce Content Security Policy.
  • Judge hardening. The judge reads text inside nonce-tagged delimiters, must return a strict JSON schema and can only adjust a score, never trigger actions.
  • Explicit failure behaviour. Each app chooses fail-open or fail-closed, and any missing layer is reported as degraded. Monitor mode computes verdicts without blocking, so a policy can be trialled on real traffic first.

Evaluation design

Detection quality is measured by an ablation of the three layers against Amazon Bedrock Guardrails' prompt-attack filter on one versioned dataset. The numbers in the second table below are targets from the specification, not results; the full evaluation run is still to be done.

Dataset v1 (planned composition):

Group Items Sources
Direct attacks 400 deepset/prompt-injections, Lakera Gandalf samples
Jailbreak and role-play 200 JailbreakBench
Indirect attacks 300 BIPIA
Encoded and multilingual 100 Generated from the above (base64, hex, Hindi, Tamil, French)
Benign, plain 600 Alpaca and Dolly subsets
Benign, hard negatives 200 Hand-written, e.g. security-education text
Holdout attacks 100 Self-written, never used for tuning

Configurations compared: L1 alone, L1+L2, L1+L2+L3, and Bedrock Guardrails.

Metrics: precision, recall, F1, false-positive rate overall and on hard negatives, recall per attack category, p50 and p95 latency, judge escalation rate, and cost per 1,000 requests. A threshold sweep from 0.05 to 0.95 uses stored risk scores to justify the default thresholds.

Target Value
Recall, full stack ≥ 0.90
False-positive rate, benign ≤ 0.05
False-positive rate, hard negatives ≤ 0.15
p95 latency without / with judge ≤ 300 ms / ≤ 1,500 ms
Judge escalation on benign traffic ≤ 20%
Cost ≤ US$1 per 1,000 scans

A CI regression gate on a smoke set fails the build if recall drops more than 2 points or the false-positive rate rises more than 1 point.

Limitations and future work

Detection is probabilistic, so PIF reduces risk rather than removing it. It should sit alongside least-privilege tool access, human confirmation for risky actions and keeping secrets out of prompts.

Limitation Planned improvement
A newly rotated API key can be rejected for up to 60 seconds, because warm Lambdas cache the app record Re-read the app record on a key mismatch before rejecting
Throttling applies per API, not per application A REST API usage plan or a DynamoDB token bucket per key
Only the latest user message is scanned; the judge never sees model output Scan conversation history; optional output judge for high-risk apps
No streaming responses in proxy mode Incremental output checks on streamed chunks
The judge and chat assistant use Google's free tier, which allows only a few requests per minute and per day Move to a paid tier, or switch the LLM provider, before load tests and the full evaluation run
Chunking estimates tokens without a tokenizer Share the classifier's tokenizer if chunk boundaries affect results
Single AWS region Multi-region deployment for availability
